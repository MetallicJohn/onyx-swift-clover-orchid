# 7. UNSAVED CHANGES — BROWSER VS IN-APP

Current behavior:

- In-app navigation → shared ConfirmDialog
- Browser refresh/tab close → browser leave prompt

This is acceptable and should remain.

However, ensure the implementation is intentional and consistent.

## In-app navigation

Use the application's shared confirmation mechanism.

Example:

```text
Unsaved changes

You have unsaved changes. Leave without saving?

[Stay] [Leave]
```

Do not use native `confirm()`.

## Browser refresh / close

Continue using the browser's native `beforeunload` mechanism where required.

Do NOT attempt to replace the browser's security-controlled leave prompt with a custom dialog; browsers do not permit arbitrary custom dialogs during tab close/refresh.

Ensure `beforeunload` is registered only while the form is actually dirty.

When saved or discarded:

```text
dirty = false
```

and the browser leave warning must disappear.

# 8. CONFIRM DIALOG MUST REMAIN OPEN WHILE ACTION EXECUTES

Current behavior:

```text
Confirm
 ↓
dialog closes
 ↓
page performs action
 ↓
page shows saving state
```

Improve this.

The shared `ConfirmDialog` must support an async confirmation lifecycle.

Correct behavior:

```text
ConfirmDialog
     ↓
User clicks Confirm
     ↓
Button becomes:
"Deleting..."
     ↓
Dialog remains open
     ↓
Action completes
     ↓
Success
     ↓
Dialog closes
```

For example:

```text
Delete Customer

This action cannot be undone.

[Cancel] [Deleting...]
```

The Confirm button must be disabled while the operation is executing.

Cancel should also be disabled during the operation.

If the operation fails:

```text
Delete Customer

Unable to delete this customer.

[Cancel] [Try Again]
```

Keep the dialog open so the user understands the operation failed.

The calling page should not need to duplicate the primary saving state.
