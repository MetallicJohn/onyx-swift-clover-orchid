# ISP Solutions — RouterOS Agent Script Generation, Permissions & Autocopy

Implement **only** the changes described in this prompt.

The goal is to fix the generated RouterOS v7 ISP Solutions agent enrollment script so it no longer depends on:

```routeros
owner=admin
```

and provide a reliable alternative for RouterOS execution permissions.

Also add an **Autocopy** button to every dialog that displays a generated script.

# 2. RouterOS Script Must Not Require `owner=admin`

The generated RouterOS v7 enrollment script must **not** contain:

```routeros
owner=admin
```

Do not assume that an `admin` user exists.

Do not make script execution depend on the username `admin`.

The generated script must work when:

* The default admin user has been renamed.
* The admin user has been disabled.
* The router uses a different administrative username.
* The router is being enrolled by another user with sufficient permissions.

---

# 3. Preferred RouterOS Agent Script Design

Generate the persistent ISP Solutions agent script without an owner requirement.

The generated script should use the existing RouterOS `/system script add` mechanism with the required execution policies.

Example pattern:

```routeros
/system script add \
    name="ispsolutions-pull" \
    policy=read,write,policy,test,password,sensitive \
    source={
        ...
    }
```

Do not include:

```routeros
owner=admin
```

The script must be executable by the scheduler.

The scheduler should also have the required policies:

```routeros
/system scheduler add \
    name="ispsolutions-agent" \
    interval=1m \
    start-time=startup \
    policy=read,write,policy,test,password,sensitive \
    on-event="/system script run ispsolutions-pull";
```

Use RouterOS v7-compatible syntax.

# 4. Alternative: Dedicated ISP Solutions User

If RouterOS requires an explicit user context for reliable agent execution in the target RouterOS version, implement the alternative using a dedicated ISP Solutions user.

The dedicated username may be derived from the router's WireGuard overlay IP.

Example:

```text
10200004
```

or another RouterOS-safe representation derived deterministically from:

```text
10.200.0.4
```

The exact implementation must produce a valid RouterOS username.

The user must have a clearly identifiable comment:

```text
ISPsolutions
```

Example:

```routeros
/user add \
    name="10200004" \
    group="full" \
    password="<generated-password>" \
    comment="ISPsolutions";
```

### Important

Do not blindly create the user if it already exists.

Make the operation idempotent:

```text
IF user exists:
    update it
ELSE:
    create it
```

Do not create duplicate users.

---

# 5. Full Rights Option

If the dedicated user approach is used, the user may use RouterOS's existing `full` group rather than creating a custom group.

Example:

```routeros
group="full"
```

This is intentional because the agent may need to perform configuration operations across:

* Interfaces
* IP addresses
* Routes
* Firewall
* NAT
* Queues
* PPP
* RADIUS
* WireGuard
* System configuration
* Router provisioning
* Monitoring
* Diagnostics

However, the generated credentials must be treated as sensitive.

Never expose the password in normal logs.

Never store it in plaintext in application logs.

Never display it outside the authenticated Superadmin/router-enrollment context.

---

# 6. Username Based on WireGuard IP

When the dedicated-user approach is enabled, derive the username from the router's assigned WireGuard overlay IP.

For example:

```text
10.200.0.4/32
```

could produce:

```text
10200004
```

The transformation must be deterministic and collision-safe within the ISP Solutions overlay.

Do not use characters that RouterOS rejects in usernames.

Store the generated username in the router enrollment record.

Do not use the router's public IP as the username.

# 7. Dedicated User Must Be Clearly Identifiable

The RouterOS user must have:

```routeros

```

or, if the repository has a standardized comment convention:


Use one consistent value throughout the system.

The backend must be able to identify the user later for:

Use the comment plus the stored router/enrollment identity where appropriate.

# 8. API Access

The generated RouterOS configuration must continue to restrict the API to the WireGuard management network.

Preferred:

```routeros
/ip service set api disabled=no port=8728 address=10.200.0.1/32;
```

Do not expose the API to the public WAN.

Firewall access must remain restricted to the ISP Solutions WireGuard controller:

```routeros
src-address=10.200.0.1
```

Example:

```routeros
/ip firewall filter add \
    chain=input \
    in-interface=wg-ispsolutions \
    protocol=tcp \
    dst-port=8728 \
    src-address=10.200.0.1 \
    action=accept \
    comment="ISP Solutions api" \
    place-before=0;
```

Do not broaden this to:

```text
0.0.0.0/0
```

or the public WAN.

# 11. Agent Script

The generated persistent agent must:

1. Download the current ISP Solutions RouterOS configuration.
2. Use HTTPS with:

   ```routeros
   check-certificate=no
   ```
3. Save the temporary script.
4. Verify that the expected file exists.
5. Import it.
6. Remove the temporary file.
7. Log only non-sensitive operational information.
8. Prevent overlapping executions.
9. Handle errors gracefully.

Do not log:

* API passwords.
* Agent tokens.
* WireGuard private keys.
* Enrollment secrets.

---

# 12. Agent Lock

Keep an execution lock to prevent multiple simultaneous agent executions.

For example:

```routeros
:global ispSolLock;

:if ($ispSolLock = true) do={
    :log warning "ISP Solutions agent already running";
    :return;
}

:set ispSolLock true;

:do {
    ...
} on-error={
    :log warning "ISP Solutions agent fetch failed";
}

:set ispSolLock false;
```

Ensure the lock is cleared even after an error.

# 13. Credential Separation

Do not confuse the following credentials:

### WireGuard

* Router private key.
* Server public key.

### Enrollment

* Short-lived enrollment token.

### Agent

* Persistent agent authentication/token.

### Router API

* Dedicated RouterOS API username/password.

Each must be handled separately.

Do not reuse the enrollment token as the RouterOS API password.
