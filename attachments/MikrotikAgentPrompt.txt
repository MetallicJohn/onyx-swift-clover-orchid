# Integrate MikroTik MCP Intelligence Engine into the Existing ISP SaaS

## OBJECTIVE

Integrate the open-source `mikrotik-mcp` project into the existing ISP Management System as the underlying MikroTik tool/execution engine for the platform's **MikroTik Assistant**.

Repository:

https://github.com/mikrotik-mcp/mikrotik-mcp

The current project provides a large RouterOS MCP tool catalogue, SSH-based router communication, multi-device support, risk classification, Safe Mode and observability capabilities. Use it as the low-level RouterOS execution layer rather than reimplementing hundreds of RouterOS operations.

The ISP application remains the authoritative layer for:

- authentication
- tenant context
- RBAC
- router ownership
- router credentials
- approval workflows
- audit logging
- change management
- customer/service context
- AI conversations
- AI tool authorization
- billing/service context
- network topology
- configuration snapshots
- rollback records

Do not rebuild the existing ISP system.

Do not remove working MikroTik functionality.

Do not replace the existing router management UI.

Integrate this as an extension of the existing MikroTik architecture.

---

Implement the following architecture:

```text
                    ISP WEB APPLICATION
                           |
                           |
                    MikroTik Assistant
                           |

                           |
              +------------+-------------+

              |                          |

              |                   Tenant validation
              |                   Router validation
              |                   Tool policy
              |                          |
              |                          v
              |                    mikrotik-mcp
              |                          |
              |                       SSH/REST
              |                          |
              v                          v
       ISP PostgreSQL               MikroTik RouterOS
```

Critical rule:

```text
AI
≠
MCP
≠
Router credentials
```

The AI must never receive raw router passwords/private keys.

The AI must never be allowed to select an arbitrary router outside the current user's authorized tenant/router scope.

# 3. DEPENDENCY

Pin a specific known-good version/commit of:

```text
@usex/mikrotik-mcp
```

Do not use an unpinned `latest` production deployment.

Record the exact version/commit in the repository.

The MCP service must be independently upgradeable from the ISP application.

Do not blindly fork the entire upstream repository unless a modification is genuinely required.

Prefer composition/configuration over maintaining a long-lived fork.

---

# 4. DO NOT TRUST MCP FOR MULTI-TENANCY

The upstream MCP server's device inventory must NOT become the SaaS tenant authorization system.

The ISP application must maintain the authoritative mapping:

```text
tenant
  |
  +-- router
       |
       +-- credential reference
       |
       +-- allowed users/roles
```

Every MCP operation must first pass through the ISP MCP Gateway.

Example:

```text
POST /api/v1/ai/mikrotik/tool
```

or the project's equivalent internal service interface.

The gateway receives:

```text
tenant_id
user_id
router_id
tool_name
arguments
request_id
conversation_id
```

Then validates:

```text
user authenticated?
tenant active?
user belongs to tenant?
user has permission?
router belongs to tenant?
router active?
tool allowed?
operation risk acceptable?
approval required?
```

Only after all checks pass should the gateway invoke the MCP server.

# 7. ROUTER CREDENTIALS

The existing ISP application must remain the source of truth for router credentials.

Do NOT place all tenant router credentials in a global static `.env`.

Do NOT store credentials in the AI conversation.

Do NOT expose credentials through MCP tool results.

Use the project's secure secret/encryption architecture.

Preferred credential model:

```text
router
    |
    +-- credential_id
              |
              v
       encrypted secret
```

Credentials should be decrypted only by the backend/MCP gateway at the moment they are needed.

Prefer SSH key authentication where practical.

Never write passwords into:

- AI prompts
- chat history
- audit logs
- tool output
- frontend state
- browser localStorage
- analytics
- error messages

# 11. READ-ONLY MODE

Implement a hard read-only mode at multiple layers.

### Layer 1

AI policy:

```text
router.ai_read_only = true
```

### Layer 2

MCP tool policy:

Only READ tools exposed/allowed.

### Layer 3

RouterOS account:

Use a restricted RouterOS account whenever possible.

### Layer 4

Application gateway:

Reject all WRITE/DESTRUCTIVE operations.

Therefore:

```text
AI says:
"Delete this firewall rule."

Gateway:
DENIED
Reason:
Router is in read-only mode.
```

Do not rely solely on the upstream MCP read-only catalogue.

The RouterOS account should provide an additional enforcement layer.

# 24. SAFE MODE

Use the upstream MikroTik MCP Safe Mode for risky RouterOS changes.

Workflow:

```text
enable_safe_mode
        ↓
apply changes
        ↓
verify
        ↓
commit_safe_mode
```

Failure:

```text
apply
 ↓
verification failed
 ↓
rollback_safe_mode
```

Safe Mode must be treated as an additional protection, not a replacement for application-level approval.

The upstream implementation uses a persistent RouterOS shell for Safe Mode and automatically reverts uncommitted changes if the session drops.

# 34. PROMPT INJECTION DEFENSE

Router data is untrusted input.

Logs, comments, hostnames, DHCP lease names and other router fields may contain text such as:

```text

```

```text

UNTRUSTED ROUTER DATA
```
