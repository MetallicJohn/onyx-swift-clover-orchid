# Add Billing → API Payments

Implement a production-ready **API Payments** module under the existing **Billing** section of the ISP Management System.

This module is the central reconciliation interface for all payments received through configured payment APIs, including but not limited to:

- M-Pesa PayBill
- M-Pesa Till
- Other configured mobile-money payment APIs
- Future payment providers that submit transactions through the platform's payment ingestion API

Do not rebuild or remove existing billing/payment functionality. Integrate this feature into the existing architecture, database, payment engine, tenant isolation, RBAC, audit logging, notifications, invoices, customer accounts and service lifecycle.

# 2. Purpose

The system must capture every valid payment transaction received through configured payment APIs.

Each transaction must initially be classified as either:

### Matched

The account/reference supplied by the customer matches an existing customer account/service/account identifier.

Display the account in **green**.

### Unmatched

The account/reference supplied by the customer does not currently match a known customer account.

Display the original account exactly as received from the payment provider, but in **red**.

Example:

```text
Transaction Code   Account        Amount
QWE123456789       IMANI1024      KES 2,000
QWE123456790       0722123456     KES 1,500
QWE123456791       IMANI-1058     KES 3,000
```

If `IMANI1024` matches a customer:

```text
IMANI1024
```

is displayed in green.

If `0722123456` does not match:

```text
0722123456
```

is displayed in red and is clickable.

# 5. Automatic Account Matching

When an API payment arrives:

1. Validate the provider payload.
2. Verify the transaction according to the existing payment-provider integration.
3. Validate amount/currency.
4. Check transaction idempotency.
5. Normalize the supplied account/reference.
6. Search the tenant's valid customer account identifiers.
7. Determine whether it matches an existing customer/service/account.
8. If matched:
   - mark the API payment as matched
   - identify the customer
   - identify the appropriate account/service/invoice
   - pass the payment into the normal payment-processing pipeline
9. If unmatched:
   - retain the payment as an unmatched API payment
   - do NOT lose the payment
   - do NOT falsely assign it
   - do NOT finalize it against another customer

# 10. Match & Process Payment

When the user confirms:

The system must execute the **same normal payment-processing pipeline used for automatically matched payments**.

Do not create a separate simplified payment path.

The processing flow should handle existing billing logic, including where applicable:

1. Match customer.
2. Match service.
3. Match invoice/account balance.
4. Create/finalize the payment.
5. Update invoice/payment status.
6. Update customer account balance.
7. Apply payment allocation.
8. Apply service renewal/payment rules.
9. Apply grace-period/service-lifecycle rules.
10. Trigger provisioning/reactivation where applicable.
11. Generate statement/ledger entries.
12. Generate applicable notifications.
13. Create audit entries.
14. Mark API payment as processed.

The exact existing business rules must remain authoritative.

---

# 11. Critical Financial Safety

Matching must be transactional.

Do not mark the API payment as processed until the complete downstream payment transaction succeeds.

Use database transactions.

If processing fails:

```text
API Payment
↓
MATCHED
↓
PROCESSING FAILED
```

rather than incorrectly reporting success.

Display the failure reason.

Allow an authorized user to retry processing without creating a duplicate payment.

---

# 12. Idempotency

API payment ingestion must be idempotent.

The same provider transaction must never create two finalized payments.

Use a unique constraint based on the provider's transaction identifier, appropriately scoped to the provider/tenant.

Example:

```text
tenant_id
provider
provider_transaction_id
```

or another provider-safe unique combination.

If the provider sends the same transaction again:

- do not create another payment
- do not duplicate ledger entries
- do not renew the service twice
- do not send duplicate payment notifications
