
# IMPLEMENTATION PROMPT — PRODUCTION ISP DASHBOARD V2

You are working on the existing multi-tenant ISP Management SaaS application.

Implement a **production-ready Dashboard V2** that replaces the current dashboard with an operational dashboard designed for ISP owners, support staff, technicians and administrators.

The uploaded `isp_dashboard_redesign_mockup.html` is the **visual and interaction reference** for the dashboard. Use its hierarchy, density, spacing, status treatment, light/dark behavior and general visual language as the design direction, but implement the dashboard using the application's existing production component system, routing, authentication, RBAC, database and APIs.

## 1. IMPORTANT IMPLEMENTATION RULES

- Do NOT rebuild the application.
- Do NOT remove working modules.
- Do NOT replace the existing authentication system.
- Do NOT create fake/demo-only dashboard data.
- Do NOT hard-code the mockup values.
- Use real tenant-scoped database/API data.
- Preserve existing multi-tenancy.
- Respect the active tenant context.
- Respect RBAC.
- Reuse existing components wherever practical.
- Do not introduce a second UI framework unnecessarily.
- Do not create a second dashboard implementation beside the existing one.
- Do not use localStorage as the source of dashboard data.
- Dashboard queries must be tenant-isolated.
- Dashboard must remain performant with thousands of customers/services and large transaction histories.
- Do not execute expensive unbounded queries on every refresh.
- Use appropriate aggregation queries, indexes and caching where required.
- All monetary values must use the application's existing financial/ledger conventions.
- All dates/times must respect the tenant's configured timezone.
- All customer data must respect existing privacy/permission rules.

The objective is an **operational command center**, not a collection of decorative statistics.
