# ISP SOLUTIONS — TICKETS PAGE REDESIGN

## Production Implementation Prompt

Redesign the existing **Tickets page** in the ISP Solutions application.

The objective is to create a cleaner, more modern, operationally efficient ticket-management interface while preserving all existing ticket functionality and business logic.

The redesigned page must include:

1. A modern ticket-management layout.
2. A prominent **New Ticket** action.
3. A **dialog/modal for creating a new ticket**.
4. Customer search inside the new-ticket dialog.
5. Customer selection before ticket details are entered.
6. Pagination for previous/existing tickets.
7. Useful filtering/search controls.
8. Responsive desktop/tablet/mobile behavior.
9. Full compatibility with the existing **Modernize** theme and existing themes.

Do not rewrite the ticketing backend unless a small API adjustment is required to support pagination or customer search.

---

# 1. MANDATORY FIRST STEP — INSPECT EXISTING IMPLEMENTATION

Before modifying anything, inspect the existing ticket implementation.

Locate the actual:

```text
ticket page
ticket components
ticket API/routes
ticket database model
ticket creation logic
ticket status logic
ticket assignment logic
customer search
technician assignment
ticket comments/replies
ticket attachments
RBAC
tenant/RLS handling
```

Likely areas include:

```text
src/routes/
src/components/isp/
src/lib/isp/
migrations/
```

Do not assume filenames.

Determine:

* how tickets are currently fetched
* how tickets are created
* how customers are identified
* existing ticket statuses
* existing priorities
* existing categories
* existing assignments
* existing ticket detail view
* existing permissions
* existing pagination, if any
* existing search utilities
* existing API contracts

Reuse existing functionality.

# 6. CUSTOMER SEARCH

The customer search must be a real backend-backed search.

Do not load the entire customer database into the browser.

Search should support existing customer identifiers such as:

* customer name
* phone number
* customer/account number
* email where applicable

Use the existing customer search API/service if one exists.

If no reusable search exists, add a minimal endpoint specifically for this purpose.

The endpoint must:

* enforce tenant isolation
* enforce RBAC
* return only necessary customer fields
* support pagination/limit
* prevent unrestricted bulk customer enumeration
* use indexed/search-friendly fields where available

# 28. CUSTOMER SEARCH PERFORMANCE

Use debouncing.

Recommended:

```text
250–350ms
```

Do not make a request on every keystroke.

Do not search until a reasonable minimum query length is reached unless the existing search system supports efficient short queries.

Example:

```text
2–3 characters minimum
```

Use the repository's established search conventions where available.

---

# 29. PERMISSIONS

Respect existing ticket permissions.

For example, if the current RBAC system allows only authorized staff to create tickets, the New Ticket button must not bypass that.

The backend must continue enforcing authorization.

Do not rely only on hiding the button.

---

# 30. TENANT ISOLATION

Customer search and ticket retrieval must remain tenant-scoped.

A staff user belonging to:

```text
Tenant A
```

must never receive:

```text
Tenant B customers
Tenant B tickets
```

through:

* customer search
* ticket search
* pagination
* filters
* direct ticket lookup

Preserve existing RLS and server-side authorization.

---

# 31. API / BACKEND REQUIREMENTS

If existing ticket APIs already support pagination/search/filtering:

**reuse them.**

If they do not, extend them minimally.

Do not create parallel APIs.

The preferred query model is conceptually:

```text
GET /tickets?
  page=1&
  pageSize=20&
  search=internet&
  status=open&
  priority=high&
  assignedTo=...
```

Use the application's existing routing/API conventions rather than blindly creating this exact endpoint.

Customer search should similarly use the existing customer API conventions.

---

# 32. DATABASE PERFORMANCE

Inspect the existing schema before modifying it.

If pagination/search requires indexes, add only the indexes justified by actual queries.

Potential searchable fields may include:

```text
ticket number
subject
customer ID
customer name
customer phone
status
priority
assigned user
created_at
updated_at
```

Do not add unnecessary indexes.

For large datasets, ensure the ticket list query does not perform expensive unbounded scans.

Do not rewrite the ticketing system.
