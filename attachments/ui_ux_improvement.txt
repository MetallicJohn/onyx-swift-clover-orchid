# UI/UX IMPROVEMENT & CONSISTENCY MILESTONE

## Objective

Improve the UI/UX of the existing ISP SaaS application to make it feel like a polished, professional, production-grade ISP management platform.

This is a **UI/UX refinement milestone**, not a backend rewrite.

Do NOT rebuild working business functionality.

Do NOT change existing database/business rules unless required to support the UI improvements.

Preserve:

- Existing authentication
- Active tenant context
- RBAC
- Customer/service relationships
- Billing logic
- Payment logic
- MikroTik functionality
- Router Agent
- Notifications
- Tickets
- Existing migrations
- Existing API/server functions

Use the existing design system, components, Tailwind conventions, icons, routing architecture and UI patterns wherever possible.

The goal is to make the entire application feel **consistent, fast, intuitive and professional**.

---

# 1. TOASTS + SHARED CONFIRMDIALOG

## 1.1 Shared Toast system

Create or standardize a global toast/notification system.

Use it consistently for:

### Success

```text
Customer created successfully
Lead converted successfully
Payment recorded successfully
Router connected
Settings saved
```

### Error

```text
Unable to save customer
Payment could not be processed
Router connection failed
```

### Warning

```text
This router has not checked in recently
This customer has an overdue invoice
```

### Informational

```text
Configuration queued for deployment
Report generation started
```

Toasts must:

- Be non-blocking
- Have accessible announcements
- Automatically dismiss where appropriate
- Allow manual dismissal
- Avoid duplicate messages
- Use consistent positioning
- Work on mobile

Do not create separate toast implementations for individual modules.

Create one reusable mechanism.

# 1.2 Replace native confirm()

Search the entire repository for:

```text

window.confirm(
```

Replace native browser confirmation dialogs with a shared:

```text

```

component.

Examples:

```text

Convert lead?

```

The dialog must support:

```text
title
description
confirmLabel
cancelLabel
variant
loading
```

Variants:

```text
default
danger
warning
```

Example:

```text

associated records may also be affected.

```

For destructive actions, the confirm button must clearly communicate the action.

Never rely solely on color.

---

# 5.1 Bulk actions must be safe

For destructive or service-impacting actions:

```text

```

Bulk actions must:

- Respect RBAC
- Respect tenant isolation
- Validate selected records
- Report partial failures
- Never silently fail

```text

```

Allow the user to inspect failures.

# IMPORTANT IMPLEMENTATION RULE

Do this as a **progressive UI modernization**, not a visual rewrite.

First inspect the existing UI/component architecture.

Then:

1. Identify existing reusable components.
2. Consolidate duplicates.
3. Build the shared primitives.
4. Apply them to Dashboard.
5. Apply them to Customers.
6. Roll them out to Services, Billing and Tickets.
7. Refactor Settings.
8. Complete mobile improvements.
9. Perform accessibility pass.
10. Run the complete test suite.

Do not change backend business logic merely to make the UI work.

Do not introduce mock data.

Do not remove existing functionality.

Do not create placeholder navigation routes.

At the end, report:

- Components created
- Components consolidated
- Routes changed
- Pages modernized
- Accessibility improvements
- Mobile improvements
- Tests run
- Test results
- Any remaining UI inconsistencies

STOP after completing this milestone and wait for the next instruction.
