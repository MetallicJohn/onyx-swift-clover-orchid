# ISP SOLUTIONS — “MODERNIZE” VISUAL THEME

## Production Implementation Specification

You are modifying the existing **ISP Solutions multi-tenant ISP management SaaS**.

Implement a new optional visual theme called:

**Modernize**

The objective is to modernize the application's visual design while preserving **100% of the existing business logic, functionality, permissions, tenant isolation, API behavior, database behavior, authentication, billing, provisioning, networking, and integrations**.

This is a **UI/design-system modernization**, not an application rewrite.

---

# 1. PRIMARY OBJECTIVE

Add a new selectable company visual theme:

> **Modernize**

The theme must be selectable from:

**Settings → Company**

Existing themes must continue working exactly as they do today.

The user must be able to switch between the existing theme(s) and:

**Modernize**

without changing application behavior or data.

The selected theme must persist at the appropriate company/tenant level using the application's existing theme/settings architecture.

Do not introduce a parallel theme system if the existing theme infrastructure can support the new theme.

# 7. EXISTING LIGHT/DARK MODE MUST REMAIN

Modernize must support both:

```text
Light
Dark
```

using the application's existing light/dark architecture.

Do not hardcode colors directly into components when a semantic token should be used.

Avoid:

```css
background: #123456;
color: #abcdef;
```

inside individual components where an existing semantic token is appropriate.

Prefer:

```css
background: var(--surface);
color: var(--foreground);
```

or the equivalent architecture already used by the repository.

# 8. MODERNIZE DESIGN PHILOSOPHY

The existing interface currently has a strong:

> SaaS-card-kit

visual language.

Modernize should deliberately reduce this.

The design principle is:

> **Hierarchy first. Cards only when they communicate structure or interaction.**

Not every section should have:

* border
* rounded rectangle
* shadow
* colored icon box

at the same time.

Use visual hierarchy instead.

---

# 9. MODERNIZE DESIGN TOKENS

Extend the existing token system rather than bypassing it.

Create or refine semantic tokens for:

### Surfaces

```text

surface
surface-subtle
surface-elevated
surface-hover
surface-active
surface-inset
```

### Text

```text
foreground
foreground-muted
foreground-subtle
foreground-disabled
```

### Borders

```text
border
border-subtle
border-strong
```

### Semantic states

```text
success
warning
danger
info
neutral
```

Each should have appropriate foreground/background/border relationships.

### Accent

The primary/accent color should have a defined purpose.

Modernize should not use the accent color indiscriminately for:

* every icon
* every badge
* every heading
* every decorative element
* every status

Reserve strong accent emphasis primarily for:

* primary CTA
* active navigation
* selected controls
* important interactive states
* key brand moments

```text

```

---

# 12. RADIUS SYSTEM

Modernize should reduce the feeling that every element is a floating rounded card.

Define semantic radius levels such as:

```text
small
medium
large
pill
```

Use:

* smaller radius for controls
* medium radius for discrete cards
* larger radius only for major surfaces where appropriate
* pill radius for badges/tags

Do not use one radius value everywhere.

---

# 13. SHADOW SYSTEM

Reduce excessive shadows.

Create semantic levels such as:

```text

subtle

```

Most normal dashboard surfaces should not require a visible shadow.

Use stronger shadows only for:

* dialogs
* popovers
* menus
* elevated interactive elements
