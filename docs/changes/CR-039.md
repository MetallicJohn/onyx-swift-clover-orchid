# CR-039 Service expiry defaults and onboarding SMS

Add Customer and Add Service share the same activation, expiry, and notification rules. Each service keeps its own account number, invoice, payment, expiry, and status.

| Surface | Behaviour |
|---|---|
| Activate after payment | Default expiry is today (Africa/Nairobi). Service stays pending / awaiting payment. No access, no active-until SMS. |
| Start as Active | Default expiry is today + package validity (30 days unless daily/weekly/hourly/yearly). Service is Active immediately. Restricted to `services.activate_now`. |
| Date picker | Calendar control, stored as YYYY-MM-DD, shown as the network date format (default dd/mm/yy). Staff edits are not overwritten when activation changes. |
| SMS | Customer Created, Service Created — Awaiting Payment, Service Created — Active, Payment Received, Payment Received for Awaiting Service, Service Activated, Restored, Suspended, Expired. De-duplicated. Failed SMS does not roll back create. |
| Payment | Awaiting line: payment-received-awaiting + activate + Service Activated. Already active: Payment Received only. Partial payment does not activate. One service’s payment never restores another. |

Proof: `onboard.test.ts`, `onboard-notify.test.ts`. Live SMS is not sent in CI (sandbox).
