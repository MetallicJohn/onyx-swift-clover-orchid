# CR-042 Continuing-client onboarding and first renewal

Imported and migrated services keep the expiry they already have. That date is the first renewal, not the day they were entered.

| Surface | Behaviour |
|---|---|
| Add customer / service | Onboarding type: new, continuing / migration, reactivation. Continuing requires the existing expiry date picker. Billing anchor = that expiry. Start as Active is allowed (already paid). Onboarding SMS off unless ticked. |
| New customers | Unchanged: after payment defaults expiry to today and issues an invoice; Active uses package validity and `services.activate_now`. |
| First renewal | `billing_anchor_date` on the service. Recurring invoices wait until today ≥ that date, then due date is the expiry, not today+14. Later renewals follow the package interval. |
| Import | CSV/TSV wizard: map columns, validate, preview (expiry + first renewal), confirm. Max 500 rows. Matching phone on continuing adds a **new service** on the existing customer and never overwrites another line’s expiry. Duplicate username skips the row. |
| Notifications | No welcome / service-created SMS unless opted in. Invoice, renewal, expiry, grace, and payment SMS still follow network settings. Failed SMS does not roll back import. |
| MikroTik | Existing username is stored and RADIUS synced. PPPoE provision and `service.changed` upserts are skipped so a live line is not bounced. |
| Expiry source | Imported expiry is `billing`, so grace, partial payment, and business credit still apply. Staff override remains for new-customer date edits. |

Permissions: import uses `customers.manage`. Continuing Active does not require `services.activate_now`. Tenant isolation unchanged.

Proof: `onboard-import.test.ts`, `onboard.test.ts`, `billing.test.ts`. Live SMS/RADIUS NAS is not sent in CI.
